Price language

MRP

Maximum retail price from the package or manufacturer. Stored tax-inclusive and required per quote line.

List Rate

Marble Park’s standard pre-discount, pre-GST selling rate from Product Master sellPrice.

Net Rate

The actual unit rate offered after discount or negotiated override, before GST.

Payable

Net Rate × quantity plus GST for a GST quotation; this is compared with tax-inclusive MRP.

Implementation sequence

Lock pricing truth, then rebuild the work surfaces

MRP, List Rate, negotiated rate, tax and fulfilment quantities must each have one source and one snapshot rule before the UI becomes the production control surface.

Detailed planAudit report
Phase 0 · Decisions

Approve pricing and migration rules

  • MRP basis by PC, box and area UOM
  • MRP mandatory on every new quote line
  • List Rate sourced from Product Master sell price
  • Legacy quote and revision policy
Phase 1 · Data contract

Persist commercial snapshots

  • Quote-line MRP and source metadata
  • List, net, tax and gross snapshots
  • Sales Order line carry-forward
  • Migration without invented MRP values
Phase 2 · Quote workflow

Make pricing complete before confirmation

  • Mandatory inline MRP capture
  • Gross-payable versus MRP validation
  • Draft allowed; confirm, PDF and send gated
  • MRP, savings and tax-correct PDFs
Phase 3 · Read models

Canonical operational queries

  • Sales Order control-tower query
  • Reserved/dispatch line query
  • Inventory product-to-lot query
  • Cursor pagination, filters and authorization
Phase 4 · Work surfaces

Polish for sales and warehouse action

  • Grouped commercial and fulfilment KPIs
  • Saved views and exception queues
  • Line drawers with next valid actions
  • Tablet and mobile operating states
Phase 5 · Release gate

Reconcile before deployment

  • GST, non-GST and UOM pricing fixtures
  • Order-to-ledger quantity proof
  • 3,000 designs and 10,000 lines
  • PDF plus desktop, tablet and mobile QA

Canonical quantity rule

One equation, every page

Ordered = open + reserved + dispatched + delivered + cancelled, with backordered as the unavailable part of open/reservation demand and returned tracked as a reverse movement. The API must return these values; frontends must not derive competing totals.
