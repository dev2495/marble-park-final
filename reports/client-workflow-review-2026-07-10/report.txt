 the API, quote-rate totals disagree between surfaces, and the database enforces one sales order and one dispatch job per
 quote.

The correct design keeps one quote and allows many controlled orders
The quote remains the negotiated customer record. Each confirmed subset becomes its own sales order, with independent
payment, reservation, procurement, document, and dispatch state. Remaining quote quantities stay available for the next order
instead of forcing a duplicate quote.

    Concurrency rule: sales-order creation must be transactional and idempotent. Two staff members cannot order the
    same remaining quantity, and retrying a request cannot create a duplicate order.


Pricing must become one business rule, not three calculations
The current quote UI and PDFs understand special rate and line discount, while sales-order totals and normalized line prices
use catalogue price. The fix should introduce one shared pricing contract used by the browser, API, quote PDF, sales-order
PDF, payments, and reports.
   Line snapshot: list price, discount percentage, final unit rate, tax rate, taxable value, tax amount, and gross line total.
   Commercial guardrail: below-floor rate requires an explicit permission or owner approval, with the requested and
   approved rate recorded.
   Version safety: editing Product Master changes future quotes only; existing quote versions and sales orders keep their
   historical rate and image snapshot.
   Single calculator: persist server-calculated totals and make both PDFs read those values instead of recalculating
   independently.

Product Master needs a real edit lifecycle
The backend already has the right first boundary because the update input does not accept SKU. The complete workflow
should add an edit action from the SKU register and product detail, expose the existing commercial fields, and close audit and
image-management gaps.
   Immutable identity: SKU is read-only in UI and rejected if supplied to update APIs; archive keeps the original SKU.
   Editable content: name, category, brand, finish, dimensions, unit, sell price, floor price, tax class, description, status,
   primary image, and gallery.
   Image controls: upload, replace, remove, set primary, reorder gallery, file validation, size limits, and durable storage.
   Audit and conflict control: record field-level before/after values and reject stale edits using a version or updated
   timestamp.

Adjacent features the client is likely to expect
  Quote fulfillment view: ordered, remaining, cancelled, reserved, pending inward, dispatched, and delivered by line and
  area.
  Price and product history: effective date, prior value, changed by, reason, and future-price scheduling.
  Duplicate active-quote warning: alert staff when the same customer and project already has an open quote; open the
  current quote instead of creating another.
  Close or cancel remainder: release stock and purchase demand with a reason, preserving the accepted order history.
  Per-order promise and payment: delivery date, payment terms, advance allocation, outstanding amount, and credit
  approval on each partial order.
  Inline customer creation and quote draft recovery: create the customer from Quote Studio, autosave drafts, and recover
  interrupted work.

Recommended Next Steps
   1. Restore a controlled production deployment first. Reconnect Railway services to source, configure health checks,
      deploy the current main revision, and verify login plus read-only core queries before client testing.
   2. Fix canonical pricing before exposing editable rate. Introduce the server pricing contract and parity tests, then make
      Rate editable in both Quote Studio and quote detail.
   3. Complete Product Master editing. Add immutable-SKU edit UI, audit history, archive behavior, safe image
      management, and focused tests.
   4. Migrate to one quote with many sales orders. Change order, reservation, dispatch, payment, procurement, and
      document ownership together, with backfill and rollback scripts.
   5. Run the isolated end-to-end release gate. Only after that gate passes should the client dataset be migrated and the
      client acceptance session begin.
