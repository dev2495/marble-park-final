Marble Park Client Workflow Readiness

Executive Summary

The client requests are valid and should be handled as one commercial workflow. Product editing, quote pricing, and partial order conversion share the same product and line snapshots; implementing them independently would create data drift.

Direct quote creation already works. Quote Studio accepts a customer and product lines without a lead or intent, while the API creates the internal CRM opportunity automatically.

Product editing, editable quote rate, and partial sales orders are not end-to-end complete. Product updates exist only in the API, quote-rate totals disagree between surfaces, and the database enforces one sales order and one dispatch job per quote.

Production is currently offline. Railway reports both application services stopped with no running replicas, so restoring a controlled deployment is the first operational action before client validation.

The correct design keeps one quote and allows many controlled orders

The quote remains the negotiated customer record. Each confirmed subset becomes its own sales order, with independent payment, reservation, procurement, document, and dispatch state. Remaining quote quantities stay available for the next order instead of forcing a duplicate quote.

QuoteFrozen commercial snapshotCustomer, area, SKU, list price, negotiated rate, tax, and accepted quantities.
SelectionChoose this orderStaff selects line quantities up to the remaining balance and confirms payment terms.
Sales orderIndependent executionEach order gets its own number, lines, payment, reservation, demand, PDF, and dispatch job.
Quote progressRemaining quantity stays openShow ordered, remaining, cancelled, and closed quantities with full order history.
Concurrency rule: sales-order creation must be transactional and idempotent. Two staff members cannot order the same remaining quantity, and retrying a request cannot create a duplicate order.

Pricing must become one business rule, not three calculations

The current quote UI and PDFs understand special rate and line discount, while sales-order totals and normalized line prices use catalogue price. The fix should introduce one shared pricing contract used by the browser, API, quote PDF, sales-order PDF, payments, and reports.

  • Line snapshot: list price, discount percentage, final unit rate, tax rate, taxable value, tax amount, and gross line total.
  • Commercial guardrail: below-floor rate requires an explicit permission or owner approval, with the requested and approved rate recorded.
  • Version safety: editing Product Master changes future quotes only; existing quote versions and sales orders keep their historical rate and image snapshot.
  • Single calculator: persist server-calculated totals and make both PDFs read those values instead of recalculating independently.

Product Master needs a real edit lifecycle

The backend already has the right first boundary because the update input does not accept SKU. The complete workflow should add an edit action from the SKU register and product detail, expose the existing commercial fields, and close audit and image-management gaps.

  • Immutable identity: SKU is read-only in UI and rejected if supplied to update APIs; archive keeps the original SKU.
  • Editable content: name, category, brand, finish, dimensions, unit, sell price, floor price, tax class, description, status, primary image, and gallery.
  • Image controls: upload, replace, remove, set primary, reorder gallery, file validation, size limits, and durable storage.
  • Audit and conflict control: record field-level before/after values and reject stale edits using a version or updated timestamp.

Full-stack review found four release blockers beyond the UI

CriticalProduction hosting

Railway shows both application services failed/stopped, zero running replicas, and no connected source repository. Public web and API domains return Application not found.

CriticalPricing integrity

Special rate and discounts are calculated in quote UI/PDF, but order totals, normalized unit price, and payment status use catalogue price. This can create customer-document and accounting disagreement.

CriticalOrder data model

Sales order and dispatch job both enforce quote ID uniqueness. Reservations and several downstream lookups are quote-scoped, so partial ordering cannot be made safe with a frontend-only change.

CriticalSecurity and uploads

Production GraphQL playground is enabled, sessions live in browser storage, login has no throttling, broad roles can upload arbitrary public files, and request bodies permit very large payloads.

HighDependency risk

Dataset: root package-lock dependency graph, including websocket, upload, mail, and CSS processing paths.

HighAutomated verification

Production builds and schema validation pass, but there are no unit or integration test files. Existing smoke scripts mutate business data and do not cover product edit, direct quote without lead, canonical rate parity, or multiple orders per quote.

HighDatabase integrity

Several normalized operational tables have IDs and indexes but no foreign keys in migrations. Partial-order work should add explicit relations and deletion rules instead of increasing soft references.

HighDelivery discipline

Service source is disconnected, health checks are absent, Docker builds use install rather than lockfile-clean install, and documentation describes older framework and authentication choices.

End-to-end acceptance must prove business truth across every surface

A release is complete only when UI, API, database state, documents, stock, payments, procurement, dispatch, and audit agree. The acceptance suite should use an isolated test database and disposable uploaded assets, never the client dataset.

Adjacent features the client is likely to expect

  • Quote fulfillment view: ordered, remaining, cancelled, reserved, pending inward, dispatched, and delivered by line and area.
  • Price and product history: effective date, prior value, changed by, reason, and future-price scheduling.
  • Duplicate active-quote warning: alert staff when the same customer and project already has an open quote; open the current quote instead of creating another.
  • Close or cancel remainder: release stock and purchase demand with a reason, preserving the accepted order history.
  • Per-order promise and payment: delivery date, payment terms, advance allocation, outstanding amount, and credit approval on each partial order.
  • Inline customer creation and quote draft recovery: create the customer from Quote Studio, autosave drafts, and recover interrupted work.

Recommended Next Steps

  1. Restore a controlled production deployment first. Reconnect Railway services to source, configure health checks, deploy the current main revision, and verify login plus read-only core queries before client testing.
  2. Fix canonical pricing before exposing editable rate. Introduce the server pricing contract and parity tests, then make Rate editable in both Quote Studio and quote detail.
  3. Complete Product Master editing. Add immutable-SKU edit UI, audit history, archive behavior, safe image management, and focused tests.
  4. Migrate to one quote with many sales orders. Change order, reservation, dispatch, payment, procurement, and document ownership together, with backfill and rollback scripts.
  5. Run the isolated end-to-end release gate. Only after that gate passes should the client dataset be migrated and the client acceptance session begin.

Decisions to confirm with the client

  • Recommended default: only admin, owner, and inventory manager can edit Product Master; sales can view and quote.
  • Recommended default: a rate below floor price requires owner approval before PDF send or order creation.
  • Recommended default: each partial order has its own payment terms, delivery promise, PDF, and dispatch job.
  • Recommended default: remaining quote quantity stays open until fully ordered or explicitly closed with a reason.
